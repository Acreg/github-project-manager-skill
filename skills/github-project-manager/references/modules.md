# 模块认领式并行开发：Release + 模块分支 + 唯一集成人

## 准备：先写唯一计划

多人开发新版本时，协调者从当前 main 创建短期 release/vX.Y.Z 分支，在此分支维护唯一活跃计划 docs/plan/计划-vX.Y.Z.md。示例表见 [模块计划模板](plan-template.md)。

计划必须包含：模块 ID、范围/验收、**独占的文件/接口列表**、依赖、智能体、认领时间、分支、状态、PR 与最新提交及实际测试。若 2 个模块都要改同一入口/合同/迁移序号，提前归集给**唯一集成人串行处理**，或显式依赖后串行；不因分支不同而允许同时覆盖共享文件。

已有历史计划的进度不可冒充当前认领：无法验证的旧工作记为“待核对”。简单的单模块修复可跳过 release 模式，直接普通 PR→main。

## 认领：GitHub 原子分支抢占是排他锁

1. 所有智能体读取 release 最新计划；只允许认领“待认领”、前置依赖满足、无共享文件冲突的模块。
2. 以 release 真实 HEAD 为起点，调用 GitHub **仅创建** Git Ref 接口创建唯一模块分支 feat/vX.Y.Z/M01：

       $repo = "OWNER/REPO"
       $release = "release/v0.1.16"
       $branch = "feat/v0.1.16/M01"
       $sha = gh api "repos/$repo/git/ref/heads/$release" --jq '.object.sha'
       gh api -X POST "repos/$repo/git/refs" -f "ref=refs/heads/$branch" -f "sha=$sha"

3. 已存在分支（409/422）表示占位，不能覆盖、force push、删除他人分支后重试。
4. **创建成功后立即登记** release 分支上唯一计划：智能体 ID、模块、认领时间、分支、独占文件、状态“开发中”。使用 GitHub Contents API 当前文件 blob SHA，并在提交后**远端读回确认**；SHA 冲突则重新读取并保留别人刚写的内容。
5. 若仅创建了分支但计划登记失败，状态记为**已占位未登记**，占位者不得开始改源码，也不能让其他人抢占。由占位者补登记或协调者核实后释放，不盲删工作。

## 模块生命周期

| 状态 | 含义 |
|---|---|
| 待认领 | 无排他分支，可按文件边界领取 |
| 开发中 | 分支抢占 + 远端计划登记成功，可在本模块范围编码 |
| 阻塞 | 保留分支，记录具体依赖/原因 |
| 完成待集成 | 测试/Commit/Push + 模块 PR→release + 远端完成标记；模块开发者停止 |
| 已集成 | 唯一集成人确认模块 PR 已合入 release 并记录 SHA |
| 待核对 | 旧进度不明，不可贸然抢做 |

开发者按里程碑实时更新 **release 分支的同一份计划**，而不是只改模块分支里的 Markdown。跨模块接口由相关负责人写契约，集成者协调变更。

## 收尾：只能一位集成人合并

1. 所有模块都“完成待集成”或“已集成”，阻塞有明确处理结论之后，唯一集成人开始合并。
2. 依依赖顺序审查各模块 PR→release，检查写入边界，合入后更新“已集成”并执行每项测试。
3. 整体编译、真实验证，发起 release/vX.Y.Z→main 总 PR；审查确认后合并，真实读回 main SHA。
4. 只有实际发布且验收通过时在发布提交打 vX.Y.Z annotated Tag；之后检查无未保存工作再清理模块和 release 分支。
5. 不增加定时心跳或模拟测试的门禁；用户要求的正常功能照实际执行。Git 版本回滚不替代生产数据和镜像回滚。

最常见异常：两个代理并发登记导致文件 SHA 冲突；见 [troubleshooting.md](troubleshooting.md)。不覆盖别人计划、不自行强推解决。
